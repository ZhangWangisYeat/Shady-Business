# Claude Code
Use `AGENTS.md` as the shared source of truth alongside Codex. Claude-only notes: avoid reading the entire `docs/` tree; load the relevant skill and contract for each task. The app uses a native Expo **development build**, not Expo Go. Do not introduce a web frontend by default.

## Running the app (Claude Code)
When asked to run, start or test the app, follow **"Run and smoke-test the app locally"** in `AGENTS.md` step by step:
- **Long-running processes:** start the emulator, uvicorn and Metro with `run_in_background`. Use an `until …; do sleep 1; done` check (boot_completed, `/api/health`, Metro `/status`) instead of plain sleeps.
- **Native build:** run `expo run:android` in the background with output redirected to a log in the scratchpad. Watch it with a Monitor that greps `BUILD SUCCESSFUL|BUILD FAILED|What went wrong|401`.
- **Screenshots:** save `adb exec-out screencap -p` captures to the scratchpad and look at them with the Read tool. Images are shown scaled, so map coordinates back to 1080×2400 before tapping.
- **Shell:** use the Bash tool for adb/emulator commands (Git Bash). Use PowerShell only for user env vars and killing stray `node.exe`.
- **Permissions:** the user has to approve SDK license acceptance and the Windows Firewall prompt themselves. The Mapbox `pk.` token comes from the user and is never generated or committed.

## Campus search and route preview (added 2026-10-17)
The search screen works like Google/Apple Maps, limited to UCLA:
- **Search card (top):** `mobile/src/search/PlaceSearch.tsx`. It has Start and Destination fields, a swap button and a dropdown that queries `GET /api/places?q=` 150 ms after typing stops (only the newest response is shown). Picking a start moves focus to the destination. Leaving a field without picking puts its previous selection back. The bottom sheet hides while a field is focused so the keyboard doesn't cover the results.
- **Auto routing:** `mobile/App.tsx` requests routes as soon as both ends are set or the temperature changes. Rapid changes collapse into one request after 250 ms, and the search animation shows for at least 700 ms. Stages are `plan → navigate → arrived`. Within `plan`, the sheet shows "Where to?", then "Finding walking routes…", then the route cards with Start and Directions side by side, then a directions list. There is no Demo walk any more (removed 2026-10-18, since the real app is what gets demoed).
- **Map:** `mobile/src/map/ShadyMap.tsx`. While routing, it shows a "marching ants" dashed line between the start and end markers. The chosen route then draws itself in (`revealSegments` in `routeDrawing.ts`, about 900 ms ease-out), and other distinct routes appear in grey. The camera is set by hand with `setCamera` whenever the view changes. Declarative `<Camera>` props didn't re-fit when the sheet grew, which hid the route. The Mapbox logo and attribution are moved above the sheet because they must stay visible.
- **Place data:** `backend/app/places/ucla_places.json` holds about 400 named OpenStreetMap features inside the UCLA boundary (ODbL; show "© OpenStreetMap contributors"). To rebuild it, run `python scripts/fetch_ucla_places.py --confirm-network` with the backend venv (one free Overpass request). `--input saved.json` re-normalizes a saved response offline. Addresses come from `attach_addresses()` in `osm_import.py`. A place uses its own OSM address, otherwise that of the addressed OSM building it sits inside, otherwise an addressed OSM feature within 15 m. Streets, walkways, artwork, gardens and plazas never borrow a neighbour's address. That covers 127 of 397 places. The rest have no address in OSM, so the dropdown shows just the category. To rebuild offline, pass both saved responses: `--input places.json --address-input addresses.json`. Normalization and the skip and category rules are in `backend/app/places/osm_import.py`, and ranking is in `catalog.py`. Don't use Google/Apple place data (their terms forbid it) or Mapbox Search (billable). See ADR-009.
- **Directions:** `backend/app/routing/directions.py` builds `steps` from OSM edge `name`/`highway`. Tests are in `backend/tests/test_directions.py` and `test_places.py`. During navigation the sheet shows the next step via `mobile/src/navigation/steps.ts`.
- **Current location vs preview (added 2026-10-17):**
  - The start defaults to `'current'` (`StartPoint = Place | 'current' | null` in `PlaceSearch.tsx`). Choosing a destination calls `currentCoordinate()` in `mobile/src/location/currentLocation.ts`, which asks for permission and takes one fix with a 10 s timeout. Fixes more than 1.5 km from campus center are rejected, and every route request gets a fresh fix. Opening a search box calls `warmUpLocation()`, which starts that fix early, only if permission is already granted and with no prompt. The route request then shares it instead of waiting on "Finding you" (about 3 s on the emulator). It's still one fix, not a watcher. The route search goes out at once when you pick a place, and only temperature changes wait 250 ms. The draw-in is 0.6–1 s, because the backend now takes about 2 s and the cards wait for the drawing. On failure the stored fix is cleared so the map doesn't show a stale dot.
  - Any other start is **preview only**: "Route preview / Compare routes" with Directions, but no Start. A "Walk there from my location" link switches back. `startGps` also refuses when the start isn't current.
  - Swap always works. Swapping "Your location → X" gives "X → Your location", a preview of the way back that uses a fresh GPS fix as the destination coordinate. The preview link then reads "Walk from my location instead" and swaps back. The start dropdown hides "Your location" while it's already the destination.
  - The map draws the fix as a blue dot (`COLORS.here`, the one colour kept on purpose).
- **Camera:** routes are fitted with `fitCamera()` (`mobile/src/map/fitCamera.ts`, Web Mercator center + zoom) and not a `bounds` stop. In rnmapbox 10.3 a bounds stop is inset by the map's current padding *and* the padding passed in, so every fit after the first came out zoomed in and hidden behind the sheet. Every camera move passes the full `padding`, because omitted edges keep their old values.
- **Sheet style:** route rows are separated by rules, not boxed cards. Recommended is listed first (`MODE_ORDER` in `App.tsx`) and gets a black bar when selected. There is no "same path" label, since the shade disclaimer covers it, and no " · " separators. Labels are small, uppercase and tracked, corners are 4 px, and the legend uses colour swatches rather than emoji. Sun exposure is a percentage of walking time from `mobile/src/plan/exposure.ts`, with unknown time reported separately and never counted as shade.
- **Rotation and heading:** pinch zoom and two-finger rotate are Mapbox defaults (set explicitly on `MapView`). While walking, only the map center follows you, so your zoom sticks; zoom 17 and tilt 50 apply once, on the first fix of a walk.
  - The blue "you" dot is a map layer with a direction beam (`mobile/src/map/heading-beam.png`, rotated with `iconRotationAlignment: 'map'`).
  - The direction comes from `useHeading()` in `mobile/src/location/heading.ts` (expo-location compass). It's called inside `ShadyMap`, not `App`, so a compass reading only re-renders the map. If no reading arrives within 2 s (emulator), it picks a random direction.
  - The compass is a black circle with a red/white needle drawn from border triangles (sharp at any density), counter-rotated by the map bearing so red points north. With no route, tapping it zooms to your location (asking for a GPS fix via `onLocate` if needed) and tapping again zooms back out. The logo (`mobile/src/brand/logo.png`) sits top-left above the search card on every screen.
  - Draw-in progress is stored with the route object it belongs to (`draw.route === active`), so a new route always starts at 0. A plain progress number left over from the last route made the whole new line flash for one frame before the animation.
  - The custom compass (top right) replaces the Mapbox one, and its job is the same whether planning or walking. With a route on screen it flips between **zoomed in on you** (zoom 18.5, tilt 45, facing your direction, centre follows you; centre and heading are sent in one camera call, because a separate heading call cancelled the centring animation and the dot drifted off centre) and **the whole route** (north-up overview fit). Without a route it flips heading-up vs north-up. Starting a walk switches to zoomed-in automatically. A manual rotate gesture stops the map turning with you but stays zoomed. While zoomed, only the centre follows you, so a pinch zoom sticks. Heading updates wait until the fly-in finishes (`flyingUntil`), because any camera call cancels the running animation. State lives in `zoomed` / `faceUp` in `ShadyMap.tsx`.
  - During a walk, **Directions** in the sheet opens the step list: passed steps are greyed, the next turn is bold. The ⌄ next to the eyebrow collapses the sheet to a bar with only the shade state and minutes left; tap the bar to expand.
  - Heading on a real Android: expo-location reads the accelerometer and magnetometer, wobbles 5–10° between readings, and only emits after a ~2° change. Sending each reading straight to the map shook the dot and the map. So `useHeading` eases toward the latest reading on its own 50 ms clock (`easeAngle`, settles in about half a second). Because the clock keeps running after readings stop, the beam still lands on the last reading. The map hears about a change only when it's 2° or more, at most every 100 ms. The random fallback runs only when `Platform.constants` says it's an emulator.
  - **Smooth walking (2026-10-18):** on the path, the dot is drawn on the route line at your progress, not at the raw fix, and steps back of under 8 m are ignored as GPS wander (`BACKTRACK_M` in `App.tsx`). Between fixes it glides (`mobile/src/map/glide.ts`, over the time since the last fix, 300–1200 ms; jumps over 40 m teleport). The glide runs in its own `YouDot` component, so the per-frame updates only re-render the dot. While zoomed in, the camera follows with `animationMode: 'linearTo'`, timed to land with the glide. Every camera call cancels the last one, and an ease restarted on each heading step stuttered, while a straight line toward the same point just carries on. The compass needle turns through an `Animated.Value`, so camera frames don't re-render the map.
  - **Lost taps:** `Button` and `Stat` used to be defined inside `App`, which made them new components on every render. A button replaced between finger-down and finger-up dropped the tap. They live at module level now, so keep any new small components out of `App`'s body too.
  - To test turning on the emulator, use **⋯ → Virtual sensors** and change the rotation. To pinch or rotate, hold Ctrl and drag on the map.
- **Intro and the walking logo (2026-10-18):** the logo's home is next to "Where to?" on the home sheet.
  - **Intro:** `mobile/src/brand/Intro.tsx` plays on launch. He walks in from the left on `#FEFEFE` (the artwork's own background), "shady business" types out letter by letter under him, then the logo glides down into his home spot. The letters are revealed by widening a clip over `wordmark.png`, with letter edges in `LETTER_ENDS`.
  - **Taps:** tapping him at home does nothing. Only two things make him walk: opening a search box from home (up to the search card) and tapping him in the card (home, and he walks down). Anything else that changes the screen, like closing the keyboard or "Plan another walk", puts him in place without a walk (`walkNext` in `App.tsx`).
  - **The trip:** `mobile/src/brand/Traveler.tsx`. He crouches, springs up and stands on the screen (rotateX with perspective, a shadow on the "floor"), walks with his back to you going up or facing you coming down, then hops back in, lands in a crouch and lies flat.
  - **Sprites:** all sheets come from `mobile/scripts/make_walk_sprites.py`, built from the icon: `walk-sheet` (side view, for the intro), `walk-back`, `walk-front`, `jump-back` and `jump-front`. They're stepped like the resume site's CSS `steps()`.
  - **Search boxes:** opening one empties it (blur puts the name back). `selectTextOnFocus` re-selected everything on every re-render on Android, so the first typed letter wiped the box.
  - Things that bit: `transformOrigin` was ignored, so the figure sits in a double-height box whose centre is his feet. Overlays need `elevation` above the card and sheet (10). Images need `fadeDuration={0}` and must stay mounted, or he blinks. The intro waits for its images' `onLoad`.
- **Recent places (2026-10-18):** focusing either search box shows up to five places you've walked to, under **Recent**, before you type. Each is just the place (name, category @ address, a small clock mark), never "A → B". Tapping one fills the focused box like a search result, and the route is calculated fresh from where you are now. Where you started is never shown, because it usually isn't where you are any more. `recentDestinations()` in `mobile/src/history/savedRoutes.ts` takes the destination of each saved route from `GET /api/routes/history`, newest first, each place once, skipping walks back to your own location. `findPlace()` in `App.tsx` looks each id up again through place search for its pin (cached per id), and the list is re-read every time a box is focused. Places already in either box are left out. The old saved-route preview ("Calculated … Shade is as it was then") was removed. The backend still stores full snapshots per ADR-010, and walks from your location are only stored when it runs with `ROUTE_HISTORY_INCLUDE_GPS=1` (test only).
- **Route cards** (`mobile/src/plan/visibleRoutes.ts`): routes within 60 s of each other merge when one has more shade (it absorbs the other) or the sun is about the same (within 15 s or 5% of the walk; the quicker one is kept). The kept card carries every merged name, e.g. "Recommended and fastest", or "Fastest and shadiest" (recommended is dropped when a route is both). An identical path, or every route at least half unknown, shows just "Fastest". A merged route whose path differs from every card already shown (at least 25% of its length more than 15 m away, checked both ways in `mobile/src/plan/pathDifference.ts`) stays as an extra card labelled "Alternate route" (numbered if more than one).
- **Route calculation speed (2026-10-17):** daytime routes were slow because of redundant geometry work, not missing data or route length alone. Each walkway edge was scored separately, and every call rebuilt the campus-wide shadow outline and intersected against all of it. The bounded shade search also scored ~3,000 nearby edges before checking whether the fastest path had full coverage, then threw that work away if it didn't. Now `scoring._outlines()` builds an STRtree of outline rings plus prepared geometries once per `ShadowField` (cached in `field.cache`), and `service.build_routes` scores the fastest path first and skips the search when it has unknown exposure. Outputs are byte-identical to before (checked on 4 routes); Alumni→Royce at 1 PM went 11.5 s → 5.1 s and Bruin Plate→Boelter 10.8 s → 2.2 s. The remaining floor is `build_shadow_field` (~3 s: 3,600 tree crowns plus buildings unioned per request).
  - **Future vision model:** a model that detects shade from images of unknown areas should add its shadow polygons to `ShadowField.shadows` and the area it vouches for to `coverage_geometry` (with its own provenance in `limitations`/`source`) inside `build_shadow_field`. Nothing else changes: those edges then score as shade/sun instead of unknown, so their routes pass the fastest-path check and get the full shade search automatically.
- **Known gaps:** pins are building centers rather than entrances, so routes can loop around a large building (e.g. Royce Hall). iOS top inset is a fixed 50 until `react-native-safe-area-context` is added in a native rebuild.
